# Caliber — Instagram Audit for Dating

An AI audit of your *existing, live* Instagram (or other platform) profile, aimed at
one outcome: making it work harder for dating. Users sign up, screenshot their
profile (bio, grid, posts — photos don't need to be on-device), and get back a
scored, specific critique generated by Claude's vision model: per-photo scoring
against proven dating-profile archetypes, a coverage check on what the audit
could and couldn't see, bio feedback with a rewrite, and prioritized next actions.

For the prioritized backlog of everything not yet built (SEO, real Stripe
billing, automated test coverage, auth hardening), see
[`OUTSTANDING_WORK.md`](./OUTSTANDING_WORK.md).

## Features

**Profile audit (core feature)**
- Upload 1–12 screenshots (JPEG/PNG/WebP) of a profile — header/bio, grid,
  individual posts, highlights, whatever's available — plus optional pasted
  bio/caption text, and pick a platform (Instagram, TikTok, X/Twitter,
  Facebook, LinkedIn, or Other; the prompt and scoring adapt to whichever is
  chosen, though the product is positioned around Instagram).
- Client-side image compression before upload (`lib/image-client.ts`) —
  downscales to a max 1568px dimension and re-encodes as JPEG (quality 0.85)
  to stay under Vercel's request-body ceiling and Claude's recommended image
  size, only when that actually shrinks the file.
- Sent to Claude (`lib/anthropic.ts`, model `claude-sonnet-5`, structured
  output validated with `zod`) for analysis. The audit returns:
  - **Coverage check** — reports what the audit could and couldn't evaluate
    across five fixed aspects (bio/header, grid, individual posts,
    highlights, video/Reels) before scoring anything.
  - **Per-photo analysis** — every photo scored and classified against a
    fixed set of 8 dating-profile photo archetypes (solo close-up, full
    body, social, activity/hobby, travel, candid, pet, style/professional),
    with strengths, issues, a dating-signal note, and a verdict
    (`feature`/`keep`/`refresh`/`retire`).
  - **Archetype coverage** — which of the 8 archetypes are present vs.
    missing from the set, with a concrete recommendation for what to shoot
    for each gap.
  - **Recommended photo order** — the same photos reordered
    best-to-feature-first.
  - **Avatar (profile picture) review** — scored separately from grid
    photos, flagging common failure patterns (mirror selfies, obscured
    faces, ambiguous group shots).
  - **Display name audit** — flags a real name vs. a handle-repeat or
    nickname/emoji stack.
  - **Bio analysis** — clarity/authenticity feedback, a verbatim transcript
    (internal-only, used for downstream checks — never shown as its own UI
    field), classification against 5 proven bio-structure archetypes
    (Professional/Entrepreneur/Traveler/Creative/Minimal) with a
    formula-shaped rewrite suggestion, a fixed bio red-flag checklist
    (quotes, height/age/zodiac, unverifiable titles, availability language,
    etc.), and a bio-link quality check.
  - **Deterministic emoji-density check** (`lib/emoji.ts`) — grapheme-aware
    (handles multi-codepoint emoji correctly), computed in code rather than
    left to the model's judgment, yielding a clean/moderate/heavy verdict.
  - **Bio-staleness nudge** (`lib/bio-staleness.ts`) — compares the current
    audit's transcribed bio against the last several audits for the same
    user and flags an unchanged bio as a signal of "nothing's happening."
  - **Profile header, grid cohesion, content strategy, and prioritized
    "top actions"** — leverage-ordered recommendations (photo fixes
    surfaced before bio wordsmithing when the photo set is the bigger gap).
- Guardrails baked into the prompt: no manipulation/deception coaching, no
  commentary on protected characteristics beyond neutral photography
  feedback, no fabricated praise — every note must be specific and
  actionable.

**Accounts & auth**
- Email/password signup and login, custom-built (bcrypt password hashing +
  signed JWT session cookie) — no third-party auth service.
- Change password (current password required) from `/dashboard/settings`.
- Logout clears the session cookie.

**Rate limiting**
- Per-user daily audit cap based on `users.plan`: 1/day on `free`, 5/day on
  `paid` (`lib/rate-limit.ts`). Returns 429 with a plan-appropriate message
  when exceeded.

**Dashboard**
- `/dashboard` — submit a new audit and view the rendered result.
- `/dashboard/history` — past audits (headline, score, date) for the
  signed-in user, newest first.
- `/dashboard/settings` — change password.

**SEO**
- Canonical site URL resolution with zero required config
  (`NEXT_PUBLIC_SITE_URL`, falling back to Vercel's own production URL).
- Generated `robots.txt` / `sitemap.xml`, `WebApplication` + `FAQPage`
  JSON-LD on the landing page, Open Graph/Twitter Card metadata, and a
  build-time-generated favicon + social-share image (no static image
  assets checked in).
- `/login`/`/signup` are crawlable but `noindex`; everything under
  `/dashboard` is `noindex` + disallowed.

**Testing**
- Vitest smoke-test suite covering auth routes, change-password, the audit
  route's validation/rate-limit/persistence paths, and core lib functions
  (auth, rate-limit, bio-staleness, emoji), with DB/Anthropic calls mocked.

**Not yet built** — see [`OUTSTANDING_WORK.md`](./OUTSTANDING_WORK.md) for
full specs: real Stripe billing (plan is a manually-set DB flag today),
login throttling, session revocation, forgot-password/email verification,
a privacy policy/ToS, component and end-to-end tests, CI, and the search
-visibility work (custom domain, Search Console, content hub, analytics).

## Tech stack

- **Next.js 16** (App Router, TypeScript) — deploy target: Vercel
- **React 18**, **Tailwind CSS 3** — no component library, no CSS-in-JS
- **Turso** (libSQL/SQLite) — `@libsql/client`, accessed only through the
  single `query()` helper in `lib/db.ts` (raw parameterized SQL, no ORM)
- **Anthropic API** (`@anthropic-ai/sdk`) for the vision analysis, with
  `zod` for structured-output validation
- Custom lightweight auth (bcrypt + signed JWT session cookie via `jose`) —
  no third-party auth service required, minimal data stored (email +
  password hash)
- **Vitest** for testing
- **npm** as the package manager (`package-lock.json` is committed)

See `OUTSTANDING_WORK.md`'s "Tech stack" section for exact pinned versions
and a list of what's deliberately *not* in this stack (no ORM, no CI yet,
no E2E framework yet, etc.).

## Local setup

```bash
npm install
cp .env.example .env.local   # fill in TURSO_DATABASE_URL, TURSO_AUTH_TOKEN, SESSION_SECRET, ANTHROPIC_API_KEY
npm run db:init              # applies schema.sql to your Turso database
npm run dev
```

Create the Turso database first if you haven't:

```bash
turso db create ig-analyzer
turso db show ig-analyzer --url       # -> TURSO_DATABASE_URL
turso db tokens create ig-analyzer    # -> TURSO_AUTH_TOKEN
```

Generate a `SESSION_SECRET` with `openssl rand -base64 32`.

Other scripts: `npm run build` (production build), `npm start` (serve a
production build), `npm run lint` (Next's ESLint config).

## Data model

Two tables, defined in `schema.sql`:

- `users` — id, email, password_hash, plan (`free` or `paid`), created_at
- `audits` — id, user_id, bio_text, photo_count, result (json text),
  transcribed_bio, created_at. `transcribed_bio` is the bio exactly as read
  by the model each audit, kept only to detect an unchanged bio across
  audits (`lib/bio-staleness.ts`) — not shown in the UI as its own field.

Photos themselves are **not** stored — they're sent to the Anthropic API for
analysis and discarded. Only the generated JSON result is persisted, keeping
the DB footprint intentionally small.

`plan` gates the daily audit cap (see below) and is set manually for now —
there's no billing integration yet (see `OUTSTANDING_WORK.md` §4). To
upgrade an account:

```sql
update users set plan = 'paid' where email = 'someone@example.com';
```

## Rate limiting

`/api/audit` enforces a per-user daily cap based on `users.plan`: **1/day on
free, 5/day on paid** (`lib/rate-limit.ts`). Exceeding it returns a 429 with
a message telling the user when to come back. There's no separate login
throttle yet.

## Account

- `/dashboard/history` lists past audits (headline, score, date) for the
  signed-in user, newest first.
- `/dashboard/settings` lets a signed-in user change their password (current
  password required). There's no email-based "forgot password" flow —
  losing your password currently means losing the account.

## SEO

- `lib/site.ts` resolves the canonical site URL with no custom domain
  required: `NEXT_PUBLIC_SITE_URL` overrides once you have one, otherwise it
  falls back to Vercel's own production URL automatically.
- `app/robots.ts` / `app/sitemap.ts` — generated `robots.txt` and
  `sitemap.xml`. Only `/` is in the sitemap; `/login` and `/signup` are
  crawlable but `noindex` (thin, near-duplicate content), and everything
  under `/dashboard` is `noindex` + disallowed (private, user-specific).
- `app/icon.tsx` / `app/opengraph-image.tsx` — favicon and social-share
  image, generated at build time (`next/og`), no static image assets needed.
- Root layout sets `metadataBase`, Open Graph, and Twitter Card metadata.
  The landing page adds `WebApplication` + `FAQPage` JSON-LD, reflecting
  content that's actually visible on the page (no undisclosed markup).
- No analytics/conversion tracking yet — deliberately deferred until there's
  a paid acquisition channel to measure.

## Deploying

1. Push this repo to GitHub.
2. Import it into Vercel.
3. Add the four env vars from `.env.example` in the Vercel project settings
   (`TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`, `SESSION_SECRET`, `ANTHROPIC_API_KEY`).
4. Run `npm run db:init` once (locally, pointed at your production Turso database)
   to create the tables before first use. Safe to re-run — it only adds
   what's missing (e.g. the `plan` column) rather than erroring on existing tables.

## Testing

```bash
npm test
```

Smoke tests (Vitest) cover the auth routes, change-password, the audit
route's validation/rate-limit/persistence paths, and the core auth/rate-limit
library functions. External calls (DB, Anthropic) are mocked — no live
Turso or Anthropic credentials are needed to run them.
